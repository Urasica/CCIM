# 문제 정의

## 반복 컨텍스트 비용

코딩 에이전트는 큰 파일을 읽은 뒤 같은 내용을 여러 턴에 걸쳐 분석, 수정, 테스트한다. 이전 `Read` 결과와 도구 출력이 매 요청에 다시 포함되면 입력 토큰·비용·지연이 누적되고, 중요한 최신 정보가 긴 로그에 묻힌다.

## 단순 요약의 신뢰 문제

코드 본문만 줄이면 호출 관계, 필드 값, 예외 조건, 실제로 호출하지 않는 경로가 빠질 수 있다. 특히 이름이 비슷한 함수군은 모델이 존재하지 않는 관계를 만들기 쉽다. 따라서 압축은 단순 텍스트 축약이 아니라 다음을 포함해야 한다.

- 원문을 식별 가능한 context로 저장한다.
- 함수 시그니처와 `CCIM fact` 같은 구조적 사실을 남긴다.
- 원문 복구 경로와 원본-압축본 매핑을 유지한다.
- 압축본만 보고 변경하려는 위험을 차단한다.

## 근거의 유효성 문제

Redis TTL 만료나 재시작, 다른 세션의 context 사용, 같은 문서의 변경 후 이전 span 재사용은 압축 자체가 성공해도 근거를 신뢰할 수 없게 만든다. CCIM은 context에 source, hash, version, session, line range를 붙이고 persistent store fallback과 evidence guard로 이 상태를 드러낸다.

## 운영 가시성 문제

토큰이 줄었다는 결과만으로는 충분하지 않다. 압축이 왜 실행·스킵됐는지, retrieve가 cache/persistent 경로 중 어디서 성공했는지, guard가 무엇을 차단했는지, 지연이 얼마나 늘었는지를 요청별로 봐야 개선과 회귀를 구분할 수 있다.

## 해결 원칙

- 유사성이나 요약 품질은 유효성의 증거가 아니다.
- 원문 복구와 버전 확인은 확정적 주장·변경 전에 우선한다.
- 불확실하거나 복구할 수 없는 context는 정상처럼 사용하지 않고 차단 또는 명시적 실패로 처리한다.
- 성능 최적화는 사실 보존과 write safety를 훼손하지 않는 범위에서만 채택한다.
